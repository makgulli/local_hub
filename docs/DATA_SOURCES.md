## 2. 선택 기능용 추가 수집 데이터

| 항목 | 내용 |
|---|---|
| 데이터명 | Open-Meteo 날씨 예보 API |
| 제공처 | Open-Meteo (https://open-meteo.com) |
| 수집일 | 실시간 호출 (별도 저장 없음, 서비스 이용 시점마다 fetch) |
| 라이선스 | CC BY 4.0 — 출처 표기 시 무료·무제한 상업적 이용 가능 (API 키 불필요) |
| 상업적 이용 여부 | 가능 (요청 한도 내, 별도 과금 없음) |
| 선정 사유 | RFP II-2 "API 비용은 제공 키 예산 범위 내에서만 운영" 제약을 위반하지 않도록, 과금·키 발급이 필요 없는 공개 API를 의도적으로 선택함 |
| 활용 방식 | `src/services/weatherService.js` 에서 구미 좌표(36.1195, 128.3446) 기준 현재 날씨 조회 → 여행 적합도 판정 |
| 출처 표기 문구 | "Weather data by Open-Meteo.com (CC BY 4.0)" |

| 항목 | 내용 |
|---|---|
| 기능명 | 페이플래너 (이동수단 요금 책정 계산, 사이드 배너) |
| 외부 API 사용 여부 | 미사용 — 브라우저 Geolocation API(출발지) + 제공 JSON의 mapx/mapy(목적지 좌표)만 사용 |
| 거리 계산 방식 | Haversine 공식(좌표 간 직선거리) × 도심 우회계수(1.3)로 도로거리 근사 |
| 선정 사유 | 당초 실습기획서에는 "카카오맵 API" 활용이 언급되어 있으나, 카카오맵 길찾기 API는 앱 키 발급과 일일 호출 쿼터·과금 정책이 있어 RFP의 예산 제약과 상충할 수 있음. weatherService.js와 동일한 원칙으로 키가 필요 없는 방식을 기본 구현으로 채택함 |
| 향후 교체 지점 | `src/services/payPlannerService.js`의 `haversineDistanceKm()`/`toRoadDistanceKm()`만 카카오 길찾기 API 호출로 교체하면, 나머지 요금 산정·UI 로직은 그대로 재사용 가능 |
| 출처 표기 | 해당 없음 (자체 계산 로직) — 요금은 국토교통부 공시 택시요금 체계를 단순화한 추정치이며 실제 요금과 다를 수 있음을 UI에 명시 |

## 3. 회사 발급 API 키 (챗봇용)

| 항목 | 내용 |
|---|---|
| 데이터/서비스명 | OpenAI Chat Completions API |
| 제공처 | OpenAI |
| 키 발급 주체 | 발주사(회사)가 발급·제공 |
| 관리 방식 | `.env` (VITE_OPENAI_API_KEY, VITE_ 접두사) — 리포지토리에는 `.env.example`만 커밋 |
| 예산/보안 조치 | 사용량 제한(rate limit)이 걸린 키만 사용, 결제 한도(Usage limit)를 낮게 설정 (RFP III-3-가) |
| 비고 | 클라이언트 번들에 키가 노출되는 구조적 한계를 팀 전원이 인지하고 있음 |

## 4. 추가 수집이 필요해질 경우의 검토 절차 (RFP III-1-나)

1. 공공데이터포털/공공누리에서 라이선스 유형(1~4유형) 확인
2. 상업적 이용 가능 여부 및 재배포/변경 가능 여부 확인
3. 팀 채널에 검토 결과 공유 후 사용 여부 결정
4. 사용 확정 시 본 문서(활용 데이터 목록)에 항목 추가
